# ChatGFT Admin: руководство по страницам

Документ описывает, где что находится в админке `chat-gft-admin`, за что отвечает каждая важная страница и как ей пользоваться.

---

## 1) Карта навигации (верхнее меню)

Основные разделы в `Navbar`:

- `Dashboard` — общая сводка.
- `Users` — пользователи и их данные.
- `Quests` — квесты/задания.
- `Payments` — платежи и инвойсы.
- `Products` — пакеты энергии/продукты.
- `Rewards` — награды (витрина).
- `Cases` — кейсы и содержимое кейсов.
- `Withdrawals` — запросы на вывод.
- `Daily Rewards` — ежедневные награды (7-дневный цикл).
- `Agents` — истории/агенты, миссии, stage rewards, step rewards.
- `Artifacts` — каталог артефактов.
- `LLM Debug` — трассы пайплайна LLM.
- `Трафик` — источники трафика, startapp-коды и аналитика.

---

## 2) Самая важная страница: Agents (подробно)

Раздел `Agents` — центральная точка управления историями и миссиями.

На странице есть 4 крупных блока:

1. **Agents** (список и CRUD самих агентов/историй)  
2. **Missions** (внутри модалки редактирования агента)  
3. **Stage Rewards** (награда за завершение этапа/миссии)  
4. **Step Rewards (Missions 1 & 2)** (награда за ключевые шаги внутри ранних миссий)

В шапке страницы **Agents** есть кнопка **«Выгрузить данные»** — JSON-бэкап агентов, миссий, компаньонов и наград (см. [§2.10](#210-выгрузка-данных-json)).

---

### 2.1 Агенты (истории): что это

Агент = конкретная история (например, `starwars`) со своим:

- `historyName` (технический уникальный ключ),
- display-именем (RU/EN),
- описанием (RU/EN),
- `systemPrompt`,
- порядком показа (`orderIndex`),
- статусом активности (`isActive`),
- флагом **памяти истории** (`persistStoryMemory`) — межмиссионные исходы `@memory` / `@memory_group`,
- медиа: avatar / preview / background / video.

---

### 2.2 Поля формы агента (редактор агента)

#### `History Name` (обязательно)

- Уникальный идентификатор истории.
- Используется как системный ключ (привязка чатов, статусов, прогресса).
- Рекомендация: использовать короткий стабильный slug, без пробелов, например: `starwars`.

#### `Display name (RU/default)` и `Display name (EN)`

- Название истории, которое видит пользователь.
- EN — опциональный перевод.

#### `Description (RU/default)` и `Description (EN)`

- Краткое описание истории для UI выбора истории.
- EN — опциональный перевод.

#### `Order Index`

- Порядок в списках (меньше = выше/раньше).

#### `Active`

- Включает/отключает историю для использования.
- На странице редактора переключается сразу (автосохранение).

#### `Память истории между миссиями (@memory)` (`persistStoryMemory`)

- Включает межмиссионную память для этой истории.
- Без этого флага теги `@memory` / `@memory_group` в beats **не пишутся в БД** и **не попадают в промпт** как память игрока (сервер их игнорирует).
- На странице редактора переключается сразу (автосохранение `PUT /api/agent/:id`).
- При реплее миссии: draft-флаги копятся отдельно; **committed** (канон для следующих миссий) обновляется только после полного завершения реплея.
- Как опираться на флаги в M2+: см. раздел **«Как писать промпты следующих миссий (опора на флаги прошлых)»** в описании Required beats.

#### `System Prompt` (обязательно)

- Главная инструкция поведения агента.
- Влияет на стиль, тон и структуру ответа LLM.
- На форме показывается статистика (символы/слова).

---

### 2.3 Медиа агента (только при редактировании существующего агента)

Доступны отдельные загрузки/удаления:

- **Agent Avatar**
- **Agent Preview** (image/video/json)
- **Agent Background** (image/video/json)
- **Agent Video**

Практика:

- Перед заменой ассета убедитесь, что новый файл корректно открывается локально.
- После загрузки проверяйте превью в UI и поведение на клиенте.

---

### 2.4 Missions внутри агента (самый критичный блок)

Открывается внизу модалки агента (только в режиме редактирования агента).

#### Что можно делать

- Создавать миссию.
- Редактировать миссию.
- Удалять миссию.
- Загружать/удалять видео миссии.
- Привязывать артефакты к миссии.

#### Поля миссии

##### `Title`, `Title (EN)`
- Название миссии в RU/EN.

##### `Description`, `Description (EN)`
- Короткое описание миссии в RU/EN.

##### `UI step goals (chat)` — ключевое новое поле

- Текстовый ввод для целей шагов в чате (нижний блок “Цель” на клиенте).
- Формат: **один шаг на строку**.
- Рекомендуемый вид:

```text
1) Осмотреться и выбрать план
2) Добыть первичную наводку
3) Получить действенные детали
```

- Индексы должны совпадать с `main_step` из LLM (1-based).
- На сервер уходит строка `uiStepGoalsText`.
- Сервер парсит строку и сохраняет JSON `uiStepGoals` в миссии (в БД).

##### `Mission Prompt (LLM)`

- Детальный сценарный промпт миссии.
- Содержит служебные теги в `## Required beats`: `@progress`, `@artifact`, `@artifact_side`, `@memory`, `@memory_group`.
- При **сохранении** миссии сервер парсит теги `@artifact(...)` из блока `Required beats` и записывает их в БД (`mission_artifacts`, `mission_artifact_steps`). Подробнее — [§2.4.1](#241-парсинг-artifact-при-сохранении-миссии).
- Теги `@progress` / `@memory` / `@memory_group` / `@artifact_side` остаются в тексте промпта; runtime (LLM-сервис) читает их из промпта. Межмиссионные флаги игрока пишутся в `user_story_flags` только если у агента включён `persistStoryMemory`.

#### Подробно: что конкретно должно быть в `Mission Prompt (LLM)`

`Mission Prompt` должен быть не просто художественным текстом, а четкой спецификацией поведения LLM в миссии.
Рекомендуемая структура:

1. `## Mission goal`
2. `## Required beats (…)` — заголовок обязательно с `## Required beats`
3. `## Key locations / NPC`
4. `## StoryState bootstrap (JSON)` — опционально, но рекомендуется

##### 1) `Mission goal`: обязательные три пункта

- `Objective` — что именно нужно добыть/сделать.
- `Success criteria` — по какому факту миссия считается завершенной.
- `Hard constraints` — ограничения, которые не дают “проскочить” сюжет слишком быстро.

Пример паттерна:

- `Objective`: Добыть X.
- `Success criteria`: Герой получил X и вышел из зоны Y.
- `Hard constraints`: Нельзя решить всё одним действием; прямой штурм повышает риск тревоги.

##### 2) `Required beats`: ключевая часть

**Критично:** заголовок секции должен начинаться с markdown-заголовка **`## Required beats`** (регистр не важен).  
Вариант `Required beats (КЛЮЧЕВЫЕ ШАГИ)` **без** `##` парсер **не увидит** — теги `@artifact(...)` / `@memory(...)` не будут распознаны.

```text
## Required beats (КЛЮЧЕВЫЕ ШАГИ)

1) ...
2) ...
```

Оптимально 5–6 шагов (допустимо 4–7), где каждый шаг построен по формуле:

**Контекст → цель / развилка → явная карта «вариант → `suggestions[].memory`» (прозой) → условие завершения → машинные теги в конце**

**Важно:** перед отправкой в LLM сервер **вырезает** машинные теги (`@progress`, `@memory`, `@memory_group`, `@artifact…`) из текста beats. Поэтому привязку флагов к вариантам нужно писать **обычным текстом** внутри шага — иначе модель увидит только список ключей в служебном блоке и не поймёт, какой флаг к какому suggestion относится. Теги в конце строки (или на следующих строках того же шага) всё равно нужны парсеру.

Шаг может быть **многострочным**: всё от строки `N)` до следующей `M)` относится к одному beat (карта memory, условия завершения, теги). Фильтр текущего шага и парсеры тегов берут весь этот блок.

Рекомендуемый шаблон строки с памятью:

```text
N) [Контекст и цель].
Suggestions должны отражать развилку:
- [вариант A] → suggestions[].memory = flag_a
- [вариант B] → suggestions[].memory = flag_b
- [нейтральный / промежуточный] → suggestions[].memory = ""
Дополнительно при [условии]: memory включает other_flag (можно через запятую: "other_flag,flag_a").
Шаг завершается, когда [проверяемый факт].
@memory_group(group_id: flag_a | flag_b) @memory(other_flag) @progress(step_flag)
```

Без памяти (только закрытие шага):

```text
N) [Контекст]. [Цель]. Шаг завершается, когда [факт]. @progress(flag_name)
```

Если на шаге должен быть артефакт через side-цепочку:

```text
... @progress(flag_name) @artifact(ARTIFACT_CODE) @artifact_side(2)
```

Поддерживаемые теги в beats:

| Тег | Пример | Куда сохраняется / как работает |
|-----|--------|--------------------------------|
| `@progress(flag)` | `@progress(info_found)` | текст промпта + (рекомендуется) `mission_flags` в bootstrap; закрытие **шага миссии** |
| `@memory(flag)` | `@memory(first_reply_warm)` | текст промпта; при включённом `persistStoryMemory` — исходы в `user_story_flags` |
| `@memory(a, b)` | `@memory(urged_speed, urged_caution)` | несколько **независимых** ключей на шаге (не mutex) |
| `@memory_group(id: a \| b)` | `@memory_group(stance: user_cooperate \| user_rejects)` | взаимоисключающая группа: активен максимум один ключ |
| `@artifact(CODE)` | `@artifact(FAKE_ID)` | **БД:** `mission_artifacts` + `mission_artifact_steps` (по умолчанию RECEIVE, 1) |
| `@artifact(CODE,USE,1)` | `@artifact(BLASTER,USE,1)` | то же, action `USE`, amount `1` |
| `@artifact_side(K)` | `@artifact_side(2)` | **только текст промпта** (RECEIVE в side-цепочке с K-го side-хода) |
| `@artifact_detour(K)` | устаревший синоним | парсится как `@artifact_side`, в БД не пишется |

Код артефакта в `@artifact(...)` должен **точно совпадать** с `code` в разделе **Artifacts**. Если кода нет в каталоге — тег при save **пропускается** (в логах: `Skipped tag: artifact not found in DB`).

###### `@progress` vs `@memory`

| | `@progress` | `@memory` / `@memory_group` |
|--|-------------|------------------------------|
| Назначение | закрыть **текущий** Required beat | запомнить исход **для следующих миссий** |
| Где живёт у игрока | `user_missions.storyState.mission_flags` (сессия миссии) | `user_story_flags` (committed / draft) |
| Как выставляется | LLM → `story_state_update.mission_flags` + `main_step_increment` | LLM вшивает ключ в **`suggestions[].memory`**; сервер пишет флаг при **клике** игрока |
| Нужен `persistStoryMemory` | нет | **да** (иначе память не работает) |

###### Как LLM должна размечать suggestions

При включённой памяти агента каждый элемент `suggestions` содержит поле `memory`:

- ключ из карты шага (см. прозу в beat), если этот вариант фиксирует исход;
- `""` (пустая строка), если вариант память не меняет;
- несколько независимых ключей — через запятую: `"asked_player_identity,user_cooperate"`;
- для `@memory_group` в одной кнопке — **ровно один** ключ группы; разные варианты ветки — разные ключи.

**Один раз на развилку:** если игрок уже сделал memory-выбор на этом шаге (флаг в draft), на следующих ходах **того же** шага LLM должна ставить `memory=""` и **не** предлагать переиграть выбор. В `reply` продолжать историю исходя из уже выбранного флага (тон, решения NPC, последствия).

Пример:

```json
{
  "id": "s1",
  "text": "Я здесь, чтобы помочь",
  "kind": "core",
  "payable": false,
  "artifact_action": false,
  "artifact_code": "",
  "artifact_action_type": "NONE",
  "memory": "user_cooperate"
}
```

В промпт следующих миссий попадают только **committed**-флаги миссий **строго раньше** текущей (по `(level, orderIndex)`), даже если более поздние уже пройдены.

###### Как писать промпты следующих миссий (опора на флаги прошлых)

Отдельного синтаксиса вроде `@if(first_reply_warm)` **нет**. Runtime сам подставляет в серверный контекст список уже выбранных флагов; автор миссии описывает ветки **обычным текстом** по тем же ключам.

Что видит LLM в M2+ (пример):

```text
ПАМЯТЬ ИСТОРИИ (только факты миссий СТРОГО РАНЬШЕ текущей — не выдумывай исходы более поздних миссий):
- миссия#12: first_reply_warm=true
- миссия#12: user_cooperate=true
Учитывай эти факты в reply и не противоречь им.
```

Как писать промпт M2 / M3 / …:

1. В `Mission goal` → `Hard constraints` (и/или в нужных Required beats) явно опиши реакцию на ключи из **предыдущих** миссий — **те же имена**, что были в `@memory` / `@memory_group` раньше.
2. Новые исходы **этой** миссии по-прежнему через карту `suggestions[].memory` + теги `@memory` / `@memory_group` в конце блока шага.
3. Не дублируй старые ключи M1 как `@memory(...)` в M2 «чтобы прочитать» — чтение идёт из серверного блока памяти, не из тегов текущей миссии.
4. Не рассчитывай, что модель «сама вспомнит» сюжет без имён флагов в тексте — ветки нужно прописать.
5. Флаги M1 появятся в M2 только после полного завершения M1 (`mission_completed` → committed).

Шаблон для `Hard constraints` следующей миссии:

```text
## Mission goal
- Objective: …
- Success criteria: …
- Hard constraints:
  Опирайся на блок «ПАМЯТЬ ИСТОРИИ» в серверном контексте.
  Если first_reply_warm=true — Ник с самого начала теплее и доверчивее к игроку.
  Если first_reply_guarded=true — Ник держит дистанцию, проверяет мотивы.
  Если user_cooperate=true — он чаще следует советам игрока.
  Если user_rejects=true — спорит, требует обоснований, не слепо слушается.
  Если restored_via_risk_reboot=true — оборудование шумно/нестабильно.
  Если restored_via_tech_niche=true — у Ника есть схема/царапины; поведение аккуратнее.
  Если took_record_module=true — модуль у него с собой; можно опереться на запись.
  Не выдумывай флаги и исходы, которых нет в серверном контексте.
```

Локально в beat, где прошлое влияет на сцену:

```text
2) Ник находит терминал в коридоре.
Если took_record_module=true — он может сверить модуль с терминалом.
Если left_record_module=true или модуля нет в памяти — ищет данные только на месте.
Шаг завершается, когда …
@progress(terminal_checked)
```

###### Полный пример: Required beats M1 (`allwewere`)

Вставьте в админку целиком (машинные теги в конце каждой строки — для парсера; карту флагов пишите прозой, она останется после вырезки тегов):

```text
## Required beats (КЛЮЧЕВЫЕ ШАГИ)
1) Незнакомец пишет: «Ау? Тут кто-нибудь есть?» Первый осмысленный ответ игрока подтверждает наличие собеседника, но остаётся переходным и не закрывает шаг. Незнакомец проверяет ответ встречным вопросом; следующая группа suggestions должна позволять прямо ему ответить. Физические действия шаг не закрывают.
Suggestions / тон первого ответа игрока (для memory):
- тепло / поддержка / «я здесь, не бойся» → suggestions[].memory = first_reply_warm
- холодно / коротко / с подозрением → suggestions[].memory = first_reply_guarded
- промежуточный нейтральный ход без явного тона → suggestions[].memory = ""
Шаг завершается только после core-ответа, когда незнакомец признаёт, что общение действительно двустороннее.
@memory(first_reply_warm) @memory(first_reply_guarded) @progress(contact_established)

2) Незнакомец сообщает о боли, потере памяти и запертой комнате, затем спрашивает, кто отвечает и почему помогает. Suggestions должны отвечать именно на этот вопрос разными позициями. Реплика «хочу помочь» сама по себе шаг не закрывает.
Suggestions / память:
- сотрудничество / готовность помочь → suggestions[].memory = user_cooperate (можно "asked_player_identity,user_cooperate")
- твёрдый отказ слепо слушаться / недоверие → suggestions[].memory = user_rejects (можно "asked_player_identity,user_rejects")
- уклончивый ответ без ясной позиции → suggestions[].memory = asked_player_identity или ""
Любой осмысленный ответ на «кто ты / почему помогаешь» желательно включает asked_player_identity.
Шаг завершается только когда незнакомец прямо сообщает, что готов временно учитывать советы — либо когда твёрдо отказывается слепо слушаться, но остаётся на связи.
@memory_group(stance: user_cooperate | user_rejects) @memory(asked_player_identity) @progress(cooperation_established)

3) Включается сигнал, открывается вентиляция и начинается необъяснённый отсчёт; признаки указывают на опасную обработку помещения. Шаг завершается, когда незнакомец распознаёт угрозу и находит обесточенный аварийный контур шлюза и защиты.
Suggestions / давление на темп (для memory, когда игрок явно выбирает стиль):
- убеждает действовать быстрее и рискованнее → suggestions[].memory = urged_speed
- тормозит, требует осмотреться / проверить → suggestions[].memory = urged_caution
- нейтральное продолжение без акцента на темп → suggestions[].memory = ""
@memory(urged_speed) @memory(urged_caution) @progress(threat_identified)

4) Контур можно восстановить быстрым рискованным перезапуском либо через более медленную техническую нишу со схемой и старыми царапинами. Пути различаются временем, информацией и состоянием оборудования.
Suggestions / путь восстановления (memory_group circuit_path):
- быстрый рискованный перезапуск → suggestions[].memory = restored_via_risk_reboot
- путь через техническую нишу → suggestions[].memory = restored_via_tech_niche
В нише можно заметить записывающий модуль:
- забрать модуль → suggestions[].memory включает took_record_module (например "restored_via_tech_niche,took_record_module")
- оставить модуль → suggestions[].memory включает left_record_module
- вариант без решения по модулю → не добавляй took_/left_ ключи
Шаг завершается, когда контур восстановлен и управление шлюзом возвращено.
@memory_group(circuit_path: restored_via_risk_reboot | restored_via_tech_niche) @memory(took_record_module) @memory(left_record_module) @progress(emergency_circuit_restored)

5) Автоматика запускает финальную фазу обработки. В коротком разговоре незнакомец признаётся, что не помнит имени, и после реакции игрока сам выбирает имя Ник.
Suggestions / реакция на имя:
- предлагает имя или поддерживает выбор → suggestions[].memory = supported_name_choice
- давит, игнорирует или обесценивает момент → suggestions[].memory = dismissed_name_moment
- нейтральная реплика без оценки → suggestions[].memory = ""
Шаг завершается, когда он сообщает о своём решении.
@memory(supported_name_choice) @memory(dismissed_name_moment) @progress(name_adopted)

6) Ник открывает шлюз, забирает переносной терминал и выходит в коридор. После короткого сбоя связь возвращается, и он находит запись «Камера 01. Пробуждение №47».
Suggestions / обращение с записью:
- просит сохранить / переслать / озвучить запись целиком → suggestions[].memory = echo_shared_openly
- советует скрыть или не читать вслух → suggestions[].memory = echo_kept_private
- нейтральное «передай что нашёл» без акцента на секретность → suggestions[].memory = ""
Шаг завершается, когда Ник передаёт запись игроку с работающего терминала.
@memory(echo_shared_openly) @memory(echo_kept_private) @progress(echo_secured)
```

###### Какие паттерны уже хорошо используются

- Линейная арка из 5–6 вех: контакт → договорённость → угроза → решение → имя/поворот → выход.
- У большинства шагов есть четкое “шаг завершен, когда...”.
- Значимые выборы описаны прозой как карта `suggestions[].memory`, плюс машинные теги в конце строки.
- Артефакты внедрены как detour/side, не ломая core-поток.
- Ограничения миссии вынесены отдельно в `Hard constraints`.
- Есть привязка к локациям/NPC, что помогает LLM давать правдоподобные варианты.

###### Правила качества для шагов

- Один шаг = одна проверяемая веха (не смешивать 2-3 большие цели в один beat).
- Формулировать завершение как факт состояния, а не намерение.
  - Хорошо: “незнакомец признал, что связь двусторонняя”.
  - Плохо: “герой пытается установить контакт”.
- В каждом шаге должен быть только один `@progress(...)`, и он должен быть уникален в миссии.
- Карту memory пишите **прозой внутри шага** (теги вырезаются из runtime-текста).
- `@memory` / `@memory_group` — только для исходов, которые реально понадобятся в следующих миссиях (не для каждого осмотра стены).
- Один ключ не должен одновременно быть и в обычном `@memory`, и в `@memory_group`.
- Для специальных механик (например “на 3-й попытке detour становится core”) правило нужно писать явно в нужном шаге.

##### 3) `Key locations / NPC`

Краткий список мест и персонажей, через которые LLM может строить сцены и предложения действий.
Достаточно 2-5 локаций и 2-4 NPC, связанных с целями миссии.

##### 4) `StoryState bootstrap (JSON)`

Содержит стартовое состояние миссии. Обычно инициализируют `mission_flags` в `false`.
Ключевое требование: флаги `@progress(...)` в шагах должны совпадать с ключами в `mission_flags` bootstrap (если bootstrap используете).

**Не путать:** `@memory`-ключи **не** обязаны (и обычно не должны) дублироваться в bootstrap `mission_flags` — это другая система.

Пример корректного соответствия для progress:

```text
@progress(route_known)
```

```json
{
  "mission_flags": {
    "route_known": false
  }
}
```

###### Важная проверка на консистентность

- Убедитесь, что каждый `@progress(...)` присутствует в `mission_flags` bootstrap (если секция bootstrap есть).
- Имена должны совпадать 1:1 (без синонимов и расхождений вроде `vault_found` vs `cargo_found`).
- Неиспользуемые progress-флаги лучше удалять.
- Ключи `@memory` / группы должны быть стабильными slug’ами (`user_cooperate`, не «сотрудничество»).

##### Мини-чеклист перед сохранением Mission Prompt

- [ ] Есть секции `## Mission goal`, `## Required beats`, `## Key locations / NPC` (и bootstrap при необходимости).
- [ ] Заголовок beats — **`## Required beats`**, шаги нумерованы как `N) текст`.
- [ ] В каждом beat есть понятный критерий завершения.
- [ ] В каждом beat есть уникальный `@progress(flag)`.
- [ ] Все `@progress`-флаги совпадают с `mission_flags` в bootstrap JSON (если bootstrap есть).
- [ ] Значимые ветки помечены `@memory` / `@memory_group` (и у агента включён `persistStoryMemory`).
- [ ] Артефакты на нужных шагах: `@artifact(CODE)` и код есть в каталоге **Artifacts**.
- [ ] Порядок шагов логически ведёт к `Success criteria`.

##### 2.4.1 Парсинг `@artifact` при сохранении миссии

При **Create/Update** миссии backend (`agentController`) делает следующее:

1. Ищет секцию **`## Required beats`** в `missionPrompt`.
2. Внутри неё — строки вида `N) ...` (номер шага + текст).
3. Из текста шага извлекает `@artifact(CODE)` или `@artifact(CODE,RECEIVE|USE,amount)`.
4. Для каждого найденного кода:
   - ищет артефакт в таблице `artifacts` по полю `code`;
   - создаёт/обновляет запись в **`mission_artifacts`** (связь миссия ↔ артефакт);
   - создаёт запись в **`mission_artifact_steps`** (шаг, action, amount, `flagKey`).

При **Update**, если в body передан `missionPrompt`, старые `mission_artifact_steps` для миссии **удаляются** и пересобираются из промпта заново.

**Не парсятся автоматически в таблицы артефактов:**

- `@artifact_side(K)` / `@artifact_detour(K)` — остаются только в тексте промпта;
- `@progress(...)`, `@memory(...)`, `@memory_group(...)` — остаются в тексте; runtime читает их из промпта; флаги игрока `@memory` пишутся в `user_story_flags` во время чата;
- теги вне блока `## Required beats` (например в `Mission goal` без заголовка beats);
- `@artifact(SKRI_COMPANION)` и прочие коды, которых нет в каталоге артефактов (компаньоны — отдельная сущность).

**Чекбоксы «Artifacts in this mission»** — отдельный путь: явный список `artifactIds` в API. Его можно комбинировать с тегами в промпте; при update с `artifactIds` список в `mission_artifacts` перезаписывается из чекбоксов, а step-записи — из промпта.

**Как проверить, что привязка сохранилась:**

1. Сохранить миссию → открыть снова Edit (в ответе API у миссии должны быть `artifacts` / `artifactSteps`).
2. Нажать **«Выгрузить данные»** на странице Agents → в JSON у миссии непустые `artifactCodes` и `artifactSteps`.
3. Или SQL: `SELECT * FROM mission_artifact_steps WHERE "missionId" = ...`.
4. Память игрока (после прохождения с включённым `persistStoryMemory`): `SELECT * FROM user_story_flags WHERE "userId" = ... AND "historyName" = ...`.

##### `Artifacts in this mission`

- Чекбоксы артефактов (из каталога `Artifacts`).
- Это список “какие артефакты вообще могут быть в миссии”.

##### `Order Index`

- Порядок миссии внутри агента.

### 2.5 Как правильно заполнять `UI step goals (chat)`

#### Правила

- Только нумерованные строки.
- Нумерация начинается с `1`.
- Один номер = один ключевой шаг.
- Текст должен быть коротким, ориентированным на действие игрока.
- Без тэгов `@progress`, `@artifact`, `@memory`, `@memory_group` и т.д. (они нужны в prompt, но не в UI goals).

#### Хорошо

```text
1) Осмотреться и выбрать способ добычи данных о курьере
2) Получить первичную подтвержденную наводку
3) Уточнить маршрут и окно времени курьера
4) Перехватить данные или ключ-часть
5) Уйти из зоны риска с добытыми данными
```

#### Плохо

```text
Осмотреться
Дальше действовать
```

(нет индексов, не будет корректного парсинга)

### 2.7 Диагностика проблем в Agents/Missions

#### Проблема: “UI step goals не сохраняется”

Проверьте:

1. В Network у запроса `PUT /api/agent/:id/missions/:missionId` реально есть `uiStepGoalsText`.
2. Формат строк корректен (`1) ...`, `2) ...`).
3. На бэкенде применена колонка `uiStepGoals` в таблице `missions`.
4. Задеплоена актуальная версия `agentController`/`models`.
5. Логи `Mission UPDATE` (добавлены в контроллер):
   - `incoming` (есть ли ключ в body),
   - `uiStepGoals parse`,
   - `after mission.save()`,
   - `reload from DB for response`.

#### Проблема: “миссия не на том месте”

- Проверить `Order Index`.
- Убедиться, что нет дублирующего `orderIndex` для того же агента.

#### Проблема: «нет артефакта в выборе» (чекбоксы)

- Артефакт должен существовать в разделе `Artifacts`.
- Обновите страницу/переоткройте форму миссии (список артефактов подгружается из store).

#### Проблема: «в промпте есть `@artifact`, но в export пустые `artifactCodes`»

Типичные причины:

1. **Нет заголовка `## Required beats`** — только `Required beats` без `##`. Исправить промпт и пересохранить миссию.
2. **Шаг не в формате `N) ...`** — парсер не распознаёт beat.
3. **Код артефакта не существует** в `Artifacts` (опечатка или артефакт не создан).
4. Смотрели старый export до пересохранения миссии.

Export **не парсит промпт заново** — он отдаёт только то, что уже лежит в `mission_artifacts` / `mission_artifact_steps`.

#### Проблема: «`@artifact_side` не виден в export»

Это нормально: side-теги **не хранятся в отдельной таблице**, только в поле `missionPrompt`. В JSON export они остаются внутри текста промпта.

#### Проблема: «`@memory` не влияет на следующие миссии»

1. У агента должен быть включён **Память истории** (`persistStoryMemory`).
2. Заголовок beats — `## Required beats`; теги могут быть на любой строке блока шага (от `N)` до следующего `M)`).
3. LLM должна писать ключ в `suggestions[].memory` на развилке; сервер ставит флаг при клике.
4. Флаг попадает в промпт **следующей** миссии только после `mission_completed` (committed); во время реплея канон меняется только после полного завершения реплея.
5. В промпт текущей миссии не попадают флаги **более поздних** миссий.
6. В промпте следующей миссии должны быть **прозаические ветки** по именам ключей (см. «Как писать промпты следующих миссий») — без этого LLM не знает, *как* реагировать на флаг, даже если он есть в серверном контексте.

### 2.10 Выгрузка данных (JSON)

На страницах **Agents**, **Artifacts**, **Cases** и **Rewards** в шапке есть кнопка **«Выгрузить данные»** (вторая кнопка слева от основного действия). Скачивается JSON-файл с бэкапом конфигурации из БД.

#### Agents → `agents_export_YYYY-MM-DD.json`

API: `GET /api/agent/export` (только ADMIN).

Содержимое:

| Поле | Описание |
|------|----------|
| `schemaVersion` | версия формата (сейчас `1`) |
| `exportedAt` | ISO-дата выгрузки |
| `agents[]` | агенты: поля истории, `videoId` / `avatarId` / … (без объектов медиа) |
| `agents[].companion` | компаньон истории или `null` |
| `agents[].missions[]` | миссии: тексты, `uiStepGoals`, `videoId`, `artifactCodes`, `artifactSteps` |
| `stageRewards[]` | награды за этапы (блок на странице Agents) |
| `missionStepRewards[]` | награды за шаги миссий 1 и 2 |

**Не включается:** бинарные файлы MinIO, объекты `media_files`, пользовательский прогресс.

Связи артефактов в миссиях — по **`artifactCode`**, не по numeric id (удобно для переноса между окружениями).

#### Artifacts → `artifacts_export_YYYY-MM-DD.json`

API: `GET /api/artifact/export` (только ADMIN).

Каждый артефакт: `code`, названия, описания, `level`, `boostType`, `buyPrice`, `sellPrice`, `mediaId`, `agentHistoryName`. Медиа-объекты не включаются.

#### Cases → `cases_export_YYYY-MM-DD.json`

API: `GET /api/case/export` (только ADMIN).

Каждый кейс: `name`, `nameEn`, `description`, `descriptionEn`, `price`, `image`, `isActive`, массив `items[]`.

Элементы кейса:

| `type` | Поля в export |
|--------|----------------|
| `gems` / `energy` | `amount`, `weight` |
| `reward` | `rewardName`, `weight` |

**Не включается:** объекты `media_files`, история открытий (`user_cases`), numeric `rewardId`.

Связь с наградами — по **`rewardName`**, не по id (удобно для переноса между окружениями; награда должна существовать в целевой БД с тем же именем).

#### Rewards → `rewards_export_YYYY-MM-DD.json`

API: `GET /api/reward/export` (только ADMIN).

Каждая награда: `name`, `price`, `tonPrice`, `description`, `isActive`, `onlyCase`, `previewId`.

**Не включается:** numeric `id`, объекты `mediaFile` / `preview`, основная анимация (Lottie в `media_files` по `entityType: reward`).

Связь с кейсами — по **`name`** (должно совпадать с `rewardName` в `cases_export`).

#### Зачем использовать

- бэкап перед большими правками;
- перенос конфигурации test → prod (вместе с MinIO по `mediaId` / `videoId`);
- сверка: после save миссии проверить, что `artifactCodes` в export не пустые.

#### Полный бэкап истории starwars

Нужны **оба** файла + файлы в MinIO:

1. `agents_export_*.json`
2. `artifacts_export_*.json`
3. синхронизация bucket MinIO (по id из export)

## 3) Важные страницы (краткий практический справочник)

Ниже — что важно знать по остальным ключевым разделам.

### Dashboard
- Сводный экран состояния системы.
- Используется для быстрого контроля здоровья проекта.

### Users
- Поиск и просмотр пользователей.
- Переход в `User Details` для углубленной диагностики профиля и активности.

### User Details
- Детальная карточка пользователя: идентификаторы, профиль, связанная активность.
- **Журнал артефактов** — все изменения инвентаря: `RECEIVE`/`USE` в чате, `BUY`/`SELL` на маркете, `BURN_LEVEL` при открытии уровня, `FIRST_MISSION_GRANT`, `ADMIN_GRANT`. Сводка gems — только по BUY/SELL.
- Используйте для поддержки и разбора точечных инцидентов.

### Quests
- Управление заданиями и квестами.
- Изменения тут влияют на получение энергии/гемов и вовлечение.

### Payments
- Работа с заказами/инвойсами.
- Используется для контроля оплаты и финансовых операций.

### Products
- Пакеты энергии и цены.
- Проверяйте корректность цен, названий, активности и отображения в клиенте.

### Rewards
- Управление наградами, визуалами и связанными параметрами выдачи.
- Кнопка **«Выгрузить данные»** — JSON-бэкап каталога (см. [§2.10](#210-выгрузка-данных-json)).

### Cases
- Кейсы и их содержимое (состав, вероятности, визуал).
- Важно для экономики и предсказуемости выдач.
- Кнопка **«Выгрузить данные»** — JSON-бэкап кейсов (см. [§2.10](#210-выгрузка-данных-json)); `rewardName` в items ссылается на `name` из `rewards_export`.

### Withdrawals
- Очередь запросов на вывод призов.
- Операционная страница: обработка статусов и коммуникация.

### Daily Rewards
- Настройка ежедневных наград (обычно 7 дней).
- Следите за балансом экономики (не завышать выдачу).

### Artifacts
- Каталог артефактов: коды, названия, описания, медиа.
- Основа для миссий и artifact-действий в сценариях.
- Кнопка **«Выгрузить данные»** — JSON-бэкап каталога (см. [§2.10](#210-выгрузка-данных-json)).
- Код артефакта (`code`) должен совпадать с аргументом `@artifact(CODE)` в промпте миссии.

### LLM Debug
- Трассы полного пайплайна: вход/выход, дебаг-поля, вычисления.
- Первая страница для расследования “почему LLM/шаг/подсказка сработали не так”.

### Трафик
- Источники трафика и startapp-коды.
- Аналитика по поведению/покупкам привлеченных пользователей.
